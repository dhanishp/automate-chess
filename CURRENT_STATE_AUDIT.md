## 2. Feature inventory

### Local / sandbox

- Implemented. The default solo/local mode creates in-memory games through `server/app/game/service.py`.
- Setup actions are validated by `AutomateRulesEngine` in `server/app/game/rules.py`.
- The React app supports same-device setup with the current board-first layout.

### Solo bot

- Implemented as an easy setup bot in `server/app/game/bot.py`.
- Bot mode supports human side choice: White, Black, or Random.
- Bot actions are generated by enumerating legal actions through the same rules engine instead of duplicating legality.
- No difficulty selection or stronger bot strategy exists yet.

### Multiplayer rooms

- Implemented at v1 level.
- Backend has in-memory room state in `server/app/game/rooms.py`.
- FastAPI exposes room create, join, get, action, leave, and WebSocket routes in `server/app/main.py`.
- One creator is assigned White and one joiner is assigned Black.
- Room state has a version counter, connected flags, player tokens, and shared `GameState`.
- Frontend has create/join UI, room session restore through `sessionStorage`, WebSocket sync, polling fallback, focus/visibility refresh, side display, room code display, and turn locking.

### LAN mode

- Partially implemented.
- `run-lan.sh` builds `client/dist`, sets `SERVE_CLIENT_DIST=1`, and serves the frontend from FastAPI on `0.0.0.0`.
- `run-dev.sh` also binds dev servers to `0.0.0.0` by default.
- LAN mode appears oriented around default port `8000`; custom ports and non-default Vite port behavior still need runtime QA.

### Deployment support

- Partially implemented for local/LAN runtime only.
- No `Dockerfile`, `render.yaml`, `render.yml`, `Procfile`, or public deployment instructions were found.
- Backend can serve the built frontend when `SERVE_CLIENT_DIST=1` and `client/dist` exists.
- Public hosted deployment is not ready without fixes to port handling, API base URL, and Stockfish installation.

### Autoplay / replay

- Implemented.
- `LocalStockfishProvider` in `server/app/game/engine.py` builds a `python-chess` board from completed setup, launches Stockfish, generates engine-vs-engine replay moves, and returns replay data.
- Frontend `AutoplayViewer` supports playback, pause/resume, restart, step forward/back, skip simulation, speed controls, clickable move list, and delayed result reveal.
- Replay data is shared in multiplayer through room state, but playback controls are local per client.

### Sample setup

- Implemented through `server/app/game/presets.py` and `/games/sample`.
- The quickstart preset creates a mid-setup sandbox where both sides have mandatory pawns and some extra pieces, no kings placed, and points left.
- Frontend exposes `Load sample setup` in non-multiplayer setup.

### UI / polish

- The current UI is a premium board-first layout with a large board column and operational sidebar.
- Light/dark theme support exists.
- SVG pieces are implemented in `client/src/components/PieceGlyph.tsx`.
- Room code, player side, waiting state, local WebSocket connection state, bot turn, calculating overlay, and replay result reveal are surfaced.
- The app still has large orchestration/style files: `client/src/screens/App.tsx` is over 1,400 lines and `client/src/theme/styles.css` is over 1,500 lines.

## 6. Multiplayer stability audit

### What looks solid

- Room creation and join are implemented and covered by backend tests.
- Each room has one shared `GameState`.
- White and Black are assigned by server.
- Actions route through `AutomateRulesEngine`.
- Wrong-side actions are rejected by `RoomService.apply_action`.
- Out-of-turn actions are rejected by the rules engine.
- WebSocket snapshots broadcast room changes.
- Frontend also performs initial room fetch, polling fallback, focus refresh, visibility refresh, heartbeat pings, and light reconnect.
- Room versioning exists and the client ignores older snapshots.
- Final king placement can broadcast a pending/running autoplay state before replay generation completes.

### What is fragile

- Player tokens are not secret in API responses. `RoomPlayerState` includes `player_token`, and full `RoomState` is sent to both players. Either client can see the opponent token in the room snapshot and submit opponent actions with direct API calls.
  - Files involved: `server/app/game/models.py`, `server/app/game/rooms.py`, `server/app/main.py`, `client/src/lib/api.ts`.

- Backend does not appear to reject setup actions before Black joins. The frontend locks White while room status is waiting, but `RoomService.apply_action` does not check `black_player` or room status before applying a token-valid White action.
  - File involved: `server/app/game/rooms.py`.

- Multiplayer Stockfish failure can leave the room stuck. `apply_room_action` broadcasts pending/running snapshots, then calls `finalize_autoplay`. If the engine is missing or fails, the endpoint raises after the room has already entered `AUTOPLAY` with `running` status. No shared `failed` state is stored or broadcast.
  - Files involved: `server/app/main.py`, `server/app/game/rooms.py`.

- Autoplay generation is synchronous inside an async FastAPI request. With default `STOCKFISH_MAX_PLIES=400` and `STOCKFISH_MOVETIME_MS=200`, worst-case generation can be slow and can block the event loop in a single-worker runtime.
  - Files involved: `server/app/main.py`, `server/app/game/engine.py`.

- `RoomService.leave_room` normalizes lookup through `_get_room`, but White-room deletion uses the original `room_code` string. A lowercase or mixed-case leave request can succeed in lookup and then fail deletion with `KeyError`.
  - File involved: `server/app/game/rooms.py`.

- Black leave behavior is inconsistent across backend/frontend expectations. Backend returns the room to waiting and keeps the same game state; frontend resets White to the launcher. The room can remain in memory abandoned by White after the UI reset.
  - Files involved: `server/app/game/rooms.py`, `client/src/screens/App.tsx`.

- If Black leaves after placing pieces and a new Black joins, the old Black setup appears to remain because `leave_room` removes only `black_player`, not Black's placed pieces.
  - File involved: `server/app/game/rooms.py`.

- WebSocket broadcast does not catch per-socket send failures. One failed socket send could interrupt a broadcast path.
  - File involved: `server/app/main.py`.

- Reconnect/session restore is minimal and sessionStorage-only. It is useful for refresh but not a complete reconnect architecture.

- `RoomStatus.COMPLETE` is assigned once phase is `AUTOPLAY`, including while autoplay is still running. That is understandable for "setup complete" but semantically blurry.

- If a king is placed in check, rules move the game to `results`, but the frontend does not appear to have a dedicated results branch. This affects local and multiplayer.
  - Files involved: `server/app/game/rules.py`, `client/src/screens/App.tsx`.

## 7. Autoplay / Stockfish audit

### How Stockfish is found/configured

- `EngineConfig.from_env()` reads:
  - `STOCKFISH_PATH`
  - `STOCKFISH_MOVETIME_MS` default `200`
  - `STOCKFISH_THREADS` default `1`
  - `STOCKFISH_HASH_MB` default `64`
  - `STOCKFISH_SKILL_LEVEL` optional
  - `STOCKFISH_MAX_PLIES` default `400`
- `LocalStockfishProvider._resolve_stockfish_path()` checks `STOCKFISH_PATH` first, then common paths:
  - `/opt/homebrew/bin/stockfish`
  - `/usr/local/bin/stockfish`
  - `/usr/bin/stockfish`
  - Homebrew cellar glob paths

### Missing Stockfish in solo mode

- Handled better than multiplayer.
- `GameService.apply_action` works on a deep copy and only persists the updated game after successful autoplay generation.
- `server/tests/test_service.py` verifies a missing engine does not store a half-completed autoplay state.
- The HTTP endpoint maps `EngineUnavailableError` to 503 for action submission.

### Missing Stockfish in multiplayer mode

- Fragile.
- The room can be moved to `AUTOPLAY` / `running` before the engine error is raised.
- The actor receives an HTTP error, but the shared room snapshot remains running.
- Non-acting clients can remain on the calculating overlay indefinitely.
- `AutoplayStatus.FAILED` exists but does not appear to be written by the multiplayer failure path.

### Can multiplayer get stuck if engine generation fails?

Yes. Based on code inspection, missing/failing Stockfish after the running snapshot can leave the room in a running autoplay state without replay data and without a shared failure snapshot.

### Should be fixed before deployment

- Store and broadcast `autoplay.status = failed` with a clear error in multiplayer.
- Keep room/game state coherent if engine generation fails.
- Consider moving replay generation off the request event loop or lowering runtime limits for the demo.
- Add backend tests for multiplayer engine-unavailable behavior.
- Add deployment configuration that installs or packages Stockfish.

- Finish setup uses `window.confirm`, which is functional but can feel rough on mobile.
- Opponent-left UX is a launcher message, not an in-room modal or reconnect-aware state.
- Missing/failing Stockfish can cause the calculating overlay to persist in multiplayer.
- `Sidebar.tsx` still contains stale fallback copy saying "Autoplay has not been implemented yet" in a non-setup branch. It may be unreachable in normal flow, but it is stale UI text.
- The frontend does not appear to have a polished display branch for `phase === "results"` if king placement immediately loses by check.
